# Домашнее задание №4: TSDB Victoria Metrics и экспорт метрик

К этому моменту курса у вас уже должно быть развёрнутое в minikube приложение из
домашнего задания №1. В рамках данной практики вам необходимо развернуть в minikube
TSDB Victoria Metrics и реализовать экспорт метрик вашего приложения.

На сегодняшний день де-факто стандартом для формата метрик является **Open Metrics**.

Метрики могут экспортироваться по одной из двух моделей:

## Pull

Веб-приложение реализует отдельный URL (как правило, `/metrics`) для мониторинга
(как правило, на выделенном порту), HTTP-запрос к которому возвращает метрики в
формате Open Metrics.

Подобный URL должен быть доступен без авторизации, но только для внутренних
запросов. Система мониторинга выполняет периодические запросы к инстансам
приложения и централизованно сохраняет метрики. Связка приложений и подобных URL
именуется **таргетом** для сбора метрик. Таргеты могут быть как статические
(заранее описаны в конфигурации системы мониторинга), так и динамические
(используют автоматическое обнаружение различными механизмами в зависимости от
окружения). Динамическое определение таргетов именуется **service discovery**.

## Push

Веб-приложение отправляет метрики в систему мониторинга при помощи запроса.
Такой подход используется заметно реже Pull-модели, так повышает нагрузку на
систему мониторинга. Используется для ситуаций, когда использование Pull-модели
не представляется возможным, например, для мониторинга периодических задач:
cron в linux, CronJob в Kubernetes, задачи в CI и т.д.

## Виды экспортёров

Существует несколько реализаций экспорта метрик, с которыми вы чаще всего будете
сталкиваться на практике:

- **готовый внешний экспортер** для какой-либо системы (СУБД, Kubernetes,
  системы сбора логов и т.д.): подключается к сервису по поддерживаемому
  протоколу и преобразует полученные данные в формат Open Metrics для последующего
  экспорта; примеры: `nginx-exporter`, `postgres-exporter` и т.д.;
- **уже реализованный в приложении «из коробки» экспортер**: СУБД или иной сервис
  предоставляет выделенный URL для сбора метрик; примеры таких систем:
  Clickhouse, RabbitMQ;
- **готовый экспортер, встраиваемый в приложение**: позволяет собирать типовые
  метрики рантайма (JVM, Node, Go) и фреймворков подключением библиотеки;
- **реализация собственных технических и бизнес-метрик** при помощи клиентских
  библиотек.

## Требования к выполнению задания

1. Установить Victoria Metrics при помощи helm-чарта по инструкции. Достаточно
   выполнить первые два шага: Grafana будет рассматриваться на следующих семинарах.
2. Реализовать экспорт метрик рантайма или фреймворка при помощи готовой библиотеки,
   или используя встроенный экспортер: actuator, django-prometheus или любой другой
   в зависимости от вашего стека.
3. Реализовать не менее четырёх бизнес-метрик в доменной области вашего приложения.
   Примеры: число успешных операций, количество заказов, число успешных авторизаций
   и т.д. Данные метрики понадобятся для выполнения последующих домашних заданий.
4. Реализовать экспорт метрик PostgreSQL, используя готовый экспортер.
   Hint: можно использовать `postgres-exporter`, добавив контейнер к поду Postgres.
   Контейнеры в поде имеют общее пространство портов. Примеры конфигурации доступны
   по ссылке.
5. Реализовать сбор всех описанных выше метрик в Victoria Metrics, используя
   service discovery, добавив аннотации `prometheus.io/` к деплойментам.
   Пример:

```yaml
# deployment.yaml (фрагмент)
spec:
  template:
    metadata:
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "8080"
        prometheus.io/path: "/metrics"
    spec:
      containers:
        - name: my-app
          image: my-app:latest
          ports:
            - name: metrics
              containerPort: 8080
```

## Артефакты

- В архиве должен быть приложен исходный код вашего приложения с реализованными метриками.
- В архиве должны быть приложены все использованные для развёртывания манифесты.
- Архив должен содержать файл `Отчёт.md` с описанием стека, использованных
  экспортеров и описанием реализованных бизнес-метрик.
- В архиве должен быть приложен короткий скринкаст с демонстрацией: вывода подов
  Victoria Metrics, демонстрацией проверки сбора метрик.
  Примеры команд:

```bash
# Проверка подов
kubectl get pods -n monitoring

# Проверка сервисов
kubectl get svc -n monitoring

# Проброс портов для доступа к VictoriaMetrics
kubectl port-forward svc/vm-single-victoria-metrics-single-server -n monitoring 8428:8428

# Проброс портов для vmagent
kubectl port-forward svc/vm-single-victoria-metrics-agent -n monitoring 8429:8429

# Проверка доступных метрик
curl "http://localhost:8428/api/v1/label/__name__/values"

# Проверка конкретных метрик приложения
curl "http://localhost:8428/api/v1/query?query=up"

# Проверка статуса скрейпинга vmagent
kubectl port-forward svc/vm-single-victoria-metrics-agent -n monitoring 8429:8429
curl "http://localhost:8429/metrics"
```
